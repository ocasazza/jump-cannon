# Evaluation Specification Scratchpad: Layout Panel Solution-Doc Comparison

User Prompt: Design a UI/UX pattern for Jump Cannon's Layout panel fitting ALL use cases; three full solution documents (solution.a.md = C2 engine capability manifests, solution.b.md = C3 per-graph-class forms, solution.c.md = C1 regime-as-data registry) to be evaluated and compared.
Artifact Type: design documents (panel IA, wireframes, data flow, use-case walkthroughs, persistence/migration, phasing)

---

## Context Analysis (Stage 1)

Let's think step by step about what these three artifacts must contain and what separates a strong expansion from a weak one.

### Explicit Requirements (from expansion contract + user instruction)
1. Panel information architecture: exact sections, controls, states.
2. Data flow: which signals/state drive rendering (TYPED_FORCE_SUMMARY, GpuForceOptions, PanelState, /compute/engines settings JSON, ?config= presets).
3. Per-use-case walkthroughs for ALL SIX: (1) vault 1k–100k+, (2) molecular UFF-typed + authored coords, (3) generated graphs, (4) untyped importer graphs, (5) remote compute engines with own settings schemas, (6) static one-shot solvers alongside live sims.
4. Persistence semantics + migration from today's PanelState (jc_layout_v1).
5. Phasing: kaizen, smallest first increment.
6. Explicit responses to every judge condition in the selection doc:
   - solution.a (C2): CK-006 (absence ≠ per-parameter provenance — merge C1 why-capsule); CK-005 (local manifests derive from existing serde schemas, not new compiled tables).
   - solution.b (C3): CK-010 (bound form count, define seventh-case behavior); hybrid-class merge behavior (partially typed graphs).
   - solution.c (C1): explicitly cover remote engines and static solvers (its pruning gate failure).
7. ASCII wireframes.
8. Faithful to the proposal's core approach (no bait-and-switch).
9. Mergeability: C1+C2 likely one pattern; B1 intent sliders a synthesis ingredient — adopt or reject with rationale.
10. Constraints: Rust+Dioxus 0.6 only, NO JavaScript; styling app.css + panel_kit::CSS; ~340–480px dockable; packages-not-crates; no engine changes for core pattern.

### Implicit Quality Expectations
- The core defect is HONESTY: dead knobs rendered live. A full solution must eliminate them everywhere, including escape/advanced surfaces (an advanced drawer full of raw GpuForceOptions knobs re-arms the lie).
- Provenance legibility: L0 data-owned / L1 regime default / L2 user intent must be visible (doctrine: "provenance visible"; fixes the false banner).
- Operate-mode doctrine: calm default, one action per screen, glanceable state, no slop.
- Ground-truth fidelity: design claims must match documented codebase facts (judges grep-verified in pruning).
- Kaizen: smallest first increment independently shippable and valuable.

### Domain Standards and Constraints
- Ground truth in layout-ux-context.md lines 17–24 (integration points), lines 26–30 (impeccable.style doctrine).
- Pruning spec (.pruning-spec.yaml) supplies the checklist idiom and gate mechanics to stay consistent with.

### Artifact Type Characteristics
Design docs: completeness and specificity are gradeable (named sections, exact controls, concrete signals, versioned migration). Vagueness ("the panel adapts appropriately") is the failure mode.

## Principles (Stage 4)

### Quality Differentiators
If all three pass every checklist item, what makes one better?
1. Depth of each walkthrough — panel state, controls present/absent, provenance shown, per case (vs. one-line coverage).
2. Structural resolution of the unit/regime collision (layered model) vs. rescaled knobs.
3. Specificity of data flow — named signals and state transitions vs. "state drives the UI".
4. Quality of the default view — glanceable, calm, one primary action.
5. Concreteness of migration — exact schema diff, version key, fallback path.
6. Real phasing — phase 1 shippable alone with user value; later phases justified.
7. Mergeability — shared vocabulary (regime/capability/why-capsule) enabling C1+C2+B1 synthesis.
8. Honesty in escape surfaces — advanced drawer filtered by the same applicability truth.

### Candidate Principles

| # | Principle | Justification | Grounded In |
|---|-----------|--------------|-------------|

| 3 | Provenance is legible per parameter (why-capsule), not just absence | Judge condition CK-006 on C2 | selection doc |
| 4 | Default view is Operate-mode calm | impeccable.style doctrine | context doc |

## RRD Refinement (Stage 6)

### Decomposition Check
| Dimension | Too Broad? | Separates BAD/GOOD? | Action |
|-----------|-----------|--------------------|--------|
| Coverage (six cases) | no — depth per case is the discriminator | yes | keep |
| Honesty incl. escape surfaces | would be broad if merged with provenance | yes | keep separate from Provenance |
| Feasibility | split: platform compliance → checklist; data-flow specificity + no-new-surface → dimension | yes | decomposed |
| UX quality | Operate-mode only; slop avoidance is checklist-verifiable | yes | keep |

### Misalignment Filtering
- Dropped "document polish/length" — length bias.
- Dropped "innovativeness" — novelty bias; doctrine demands boring.

### Redundancy Filtering
- Provenance vs. Honesty: correlated but distinct observable (absence vs. explanation). Keep both; down-weight provenance slightly.
- Feasibility vs. Migration: distinct (build vs. upgrade path). Keep.

### Weight Optimization
8 dimensions. Coverage + Honesty are the decisive axes (pruning gate + core defect): 0.16 + 0.18. Provenance 0.12, Operate UX 0.12, Feasibility 0.12, Migration 0.12, Kaizen 0.08, Mergeability 0.10. Sum = 1.00. Correlation adjustment: Provenance–Honesty correlated (~0.6, below 0.7 threshold) — no reduction.

**Total weight: 1.0**
