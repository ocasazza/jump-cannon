# Evaluation Specification Scratchpad: Pruning spec for Layout-panel UX proposals

User Prompt: Design a UI/UX pattern for Jump Cannon's Layout panel fitting ALL six use cases, replacing the flat physics-constants panel whose knobs lie when importer data owns simulation dimensions. Constraints: Rust+Dioxus only, app.css + panel_kit::CSS, 340–480px dockable panel, impeccable.style Operate-mode doctrine.
Artifact Type: proposals (high-level UI/UX approaches with probability estimates, not implementations). Judges use this spec to select the top 3 of many proposals for full development.

---

## Context Analysis (Stage 1)

### Explicit Requirements (from the goal + user prompt)
- R1: Fits ALL six use cases: (1) Obsidian vault graphs 1k–100k+ nodes (default), (2) molecular graphs with UFF-typed bonds/atoms + authored coordinates, (3) generated graphs, (4) untyped importer graphs (K8s/OKF/httpjson, vault-like), (5) remote engines with own settings schemas, (6) static one-shot solvers vs live sims.
- R2: Replaces the broken flat-physics-constants mental model; root cause is three parameter LAYERS rendered as one flat form: L0 data-owned (UFF rests/weights, authored positions), L1 regime defaults (for_n_nodes, ?config= presets, Fast/Balanced/Pretty), L2 user intent.
- R3: No dead knobs: when L0 fully covers a dimension, the L1/L2 knob for it must not render live (spring_len slider with 25/25 UFF bonds is the canonical lie).
- R4: Correct regime/unit handling: vault-scaled repulsion colliding with ångström geometry must be resolved structurally, not by rescaling.
- R5: Rust+Dioxus 0.6 only; NO JS/TS anywhere; styling only in app/ui/assets/app.css + panel_kit::CSS.
- R6: ~340–480px dockable panel-kit panel; calm by default, one action per screen.
- R7: impeccable.style Operate-mode doctrine: frequent actions easy to find/carry out; state legible at a glance; labels over placeholders; provenance visible; anti-slop (no nested cards, icon-tile stacks, eyebrow chips, gradient accents, decorative motion).
- R8: Core pattern needs no JS, no new crates, no engine changes; "packages, not crates": configuration/data over new compiled surface.
- R9 (proposal contract): each proposal has name + one-sentence summary; 2–3 paragraph detailed description; key design decisions + rationale; trade-offs; probability estimate; complexity (low/medium/high); risks and failure modes.
- R10: Proposals are approaches, NOT implementations.

### Implicit Quality Expectations
- One universal pattern, not per-importer special-cased panels.
- Preserves/respects existing integration points: PanelState localStorage `jc_layout_v1`, `?config=` boot presets, TYPED_FORCE_SUMMARY signal, `/compute/engines` settings JSON.
- Honest risk assessment incl. migration of persisted state and preset detection (`LayoutPreset::detect` fingerprints).
- Proposal is discriminable: a judge can tell what would be built.

### Domain Standards and Constraints (verified in repo)
- layout.rs 4199 lines; sliders rendered flat (spring_k, spring_len log 1..10_000, gravity, damping, ...); presets Fast/Balanced/Pretty with spring_len 40/60/80; banner at TYPED_FORCE_SUMMARY claims "sliders scale on top" (false).
- `GpuForceOptions::for_n_nodes(n)` lazy-init; `active_spring_len` reads persisted state to anchor authored-coordinate rescale — any design must keep this contract working.
- Remote bridge engines supply per-engine settings JSON via graph-compute.

### Artifact Type Characteristics
High-level proposals: quality = correct problem model, universal coverage, feasibility within constraints, UX doctrine fit, honest trade-offs/risks, minimal sufficient mechanism. NOT: code, pixel specs, exhaustive detail.

## Principles (Stage 4)

If two proposals both pass every checklist item, the better one:
- P1: Uses ONE mechanism (e.g., a capability/provenance pass) that generalizes across all six cases rather than enumerating cases.
- P2: Models the three parameter layers explicitly and correctly (L0/L1/L2), incl. who wins on collision.
- P3: Achieves Operate-mode glanceability: default view is small, state legible, advanced tucked away.
- P4: Data-driven over hardcoded (packages-not-crates): derives from existing signals/schemas, no per-engine compiled tables.
- P5: Smallest sufficient pattern (kaizen): replaces the flat form; doesn't pile modes on top.
- P6: Honest risk/migration treatment of persisted state, preset detection, remote schema drift.

## Rubric Dimensions (Stage 5)

### Contrastive Examples (Step 5.1 — BAD FIRST)

#### BAD Example
```
Name: Smart Range Rescaling
Summary: Keep the flat slider form; auto-rescale slider ranges when TYPED_FORCE_SUMMARY is non-empty.
Description: The panel stays as-is: one flat list of physics sliders plus Fast/Balanced/Pretty
presets. On graph load, if typed data is present, we multiply spring_len/repulsion slider
min/max by 0.02 so values look like ångströms. A "Molecular mode" checkbox switches presets to
molecule-tuned copies. Remote engines and static solvers keep their existing flat forms; we add
per-engine hardcoded range tables compiled into the panel as needed.
Decisions: minimal churn to layout.rs; reuse existing Slider component.
Trade-offs: low effort; structure unchanged. Probability 0.9. Complexity low.
Risks: minimal code churn, low risk overall.
```

#### GOOD Example
```
Name: Provenance-Layered Intent Panel
Summary: One panel in three layers — a provenance header showing what the data owns, a small
intent row ("spread out / settle faster") mapped to engine parameters, and a collapsed advanced
drawer rendering only knobs that are live for the current graph.
Description: The panel derives a per-graph capability table from TYPED_FORCE_SUMMARY + engine
kind + node count: each parameter is tagged data-owned / regime-default / user-adjustable.
Data-owned dimensions render as provenance text ("25 bond lengths from UFF import"), never as
sliders; regime defaults come from for_n_nodes / ?config= and show as baseline. Vault graphs get
the full physics drawer (nothing data-owned); molecules get a near-empty drawer with
gravity/cooling hidden; remote engines contribute their settings-JSON knobs through the same
capability pass; static solvers show a one-shot "Solve" action. Presets become regime-named
("Vault 10k", "Molecular UFF") so wrong-regime presets can't be applied to typed graphs. State
stays in PanelState jc_layout_v1; implemented with existing Slider/panel-kit components, no
engine changes, ~300 lines in layout.rs.
Trade-offs: rewrites the gpu-force section; capability derivation must stay in sync with importers.
Probability 0.85. Complexity medium.
Risks: jc_layout_v1 payloads lacking capability tags fall back to for_n_nodes; renaming presets
breaks LayoutPreset::detect fingerprinting — detection moves to explicit regime fields; remote
engines with exotic settings JSON get a generic fallback group.
```

### Misalignment Filtering
- Dropped candidate "Proposal completeness/detail depth" as a rubric: rewards length; kept as binary CK-008 instead.
- Dropped candidate "Novelty/ambition": novelty bias; doctrine rewards boring correctness.
- Probability-estimate accuracy not scored: unverifiable at pruning time; realism folded into D6 only via risk honesty, not numeric probability.

### Redundancy Filtering
- D3 (feasibility/data-driven) vs D5 (minimality): correlated (~0.5) but distinct — a proposal can be minimal yet need engine changes, or data-driven yet sprawling. Keep both; down-weight D5 slightly.
- D2 vs CK-002: checklist gates binary presence; D2 scores depth of the layered model (collision precedence, unit regimes). No double-count.
