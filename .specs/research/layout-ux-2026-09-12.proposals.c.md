# Explorer C proposals — Layout panel UI/UX (system/architecture leans + unconventional)

Context: `.specs/research/layout-ux-context.md`. NOTE: generated in-session after subagent quota failures; independence degraded vs the ToT ideal.

---

## C1 — Regime-as-data registry (named regimes are YAML packages, auto-resolved)

**Summary:** Regimes become declarative YAML packages (generalizing `app/configs/caffeine-uff.yaml`) with auto-resolution rules; the panel is a regime picker + provenance display + small override surface.

Today `caffeine-uff.yaml` is a one-off boot preset. C1 makes it a *kind of thing*: a `regimes/` directory of named YAML packages — `molecular-uff.yaml`, `vault-large.yaml`, `vault-small.yaml`, `fast.yaml`, `balanced.yaml`, `pretty.yaml` — each declaring its engine, option values, applicability predicates (typed-data present, node-count band, graph source kind), and which controls it exposes. A resolver picks the default regime from the loaded graph (typed UFF data → molecular-uff; n>10k → vault-large; else vault-small). The panel renders: regime capsule (name + one-line description + provenance), a regime picker (from the registry, not hardcoded), and only the controls the regime declares meaningful. Fast/Balanced/Pretty migrate from hardcoded Rust to registry entries — new regimes become data, not code, honoring "packages, not crates".

Key decisions: (1) regime definition and applicability are data, deployed and iterated without recompiling the app; (2) auto-resolution with visible override (the capsule always says *why* this regime: "25/25 bonds UFF-typed"); (3) regimes declare their own control surface — dead knobs are absent by construction, not suppressed. Trade-offs: resolver predicates need a small evaluation ruleset (keep it boring: ordered predicates, first match wins); registry and `?config` preset formats must converge (one YAML schema, not two); engine-specific option typing in YAML needs the same serde coverage the options structs have (mostly present). **Probability 0.85. Complexity medium.** Risks: predicate ordering bugs pick wrong regimes silently; two overlapping config systems during migration (boot presets vs registry); YAML expressiveness pressure (predicates want to become a language — must resist).

## C2 — Engine capability declarations (panel renders strictly from what each engine declares)

**Summary:** Every engine ships a capability manifest — which dimensions it consumes, which the data owns, which controls are meaningful at what graph sizes — and the panel renders itself from the manifest; no manifest-driven rendering, no lies.

The lying-slider defect generalized: the panel hardcodes GpuForceOptions' knobs and shows them for every engine and graph. C2 moves the truth into per-engine manifests (JSON, served alongside `/compute/engines` for remotes, compiled-in for locals): dimensions consumed (`spring_len`: used only for untyped edges), applicability (`repulsion_backend`: meaningful only n>500), units (`rest lengths: data-unit`), and interactions (damping × cooling). The panel renders controls exactly when manifest ∧ graph state say they're live: 25/25 typed bonds → spring_len control not emitted; 24 nodes → backend selector not emitted. It's the type-system approach to UI honesty: inapplicable controls are unrepresentable because they're never constructed.

Key decisions: (1) manifest as the single source of control-applicability truth, shared by local and remote engines; (2) graph-state predicates (typed coverage, n) evaluated at render, not at engine init — reload-safe; (3) manifests versioned with the engine. Trade-offs: manifest schema design is real upfront work (and wants to grow into a form-builder DSL — scope tightly); local engines' manifests duplicate information already in Rust types (two sources to keep in sync unless generated); remote engines must adopt the manifest or render as today. **Probability 0.80. Complexity medium.** Risks: manifest/Rust drift (mitigate: generate manifest from the options struct via serde where possible); schema creep into a UI framework; remote engines without manifests get a degraded-but-honest fallback form.

## C3 — Per-graph-class forms (honest specialization over false generality)

**Summary:** Accept that one form can't serve all classes: the panel switches between a small number of purpose-built forms — Vault, Molecular, Remote, Static — selected by graph class, each showing only what that class needs.

The inversion of "one pattern fits all": the *pattern* is the switching, not the form. Vault form: today's sliders (they're honest there). Molecular form: UFF summary (element/bond counts), global geometry scale slider (the one physically meaningful global), element-weighted repulsion strength, "keep authored 3D" toggle — no cooling/halt/backend (converges instantly, exact pairs). Remote form: the engine's own settings JSON rendered generically. Static form: solve button + quality preset only. Class detection: typed-data presence, graph size, engine kind — same predicates as C1's resolver but driving whole forms instead of one adaptive form.

Key decisions: (1) forms are small and honest rather than one adaptive mega-form; (2) class detection is automatic with manual override; (3) shared components (slider row, provenance chip) keep forms consistent — same parts, different assemblies. Trade-offs: N forms to maintain (bounded at 4, shared components mitigate); class-boundary graphs (partially typed) need a defined merge behavior (show both sections?); "the pattern fits all use cases" is satisfied by the meta-pattern, which some will read as sidestepping the brief. **Probability 0.80. Complexity low.** Risks: form proliferation pressure (every new graph class wants its own — must gate on real need); inconsistent idioms creeping between forms; hybrid-class UX unresolved.

## C4 — Units normalization in the engine (sim always runs in data units; all UI dimensionless)

**Summary:** The engine normalizes any graph into its own natural units (authored scale, for_n_nodes scale) and every user-facing control becomes a dimensionless multiplier around 1.0 — "spring_len 53.56 vs UFF 1.4 Å" stops being a category the UI can express.

The root defect is that the UI traffics in absolute units while the graph's natural unit varies by class and source. C4 fixes it at the engine boundary: at init, the engine computes a base scale (authored mean bond for authored graphs, for_n_nodes spring_len otherwise) and normalizes all positions/rests internally; every option that was absolute becomes relative (bond scale ×1.0, repulsion strength ×1.0, gravity ×1.0). The UI can then never present a vault-tuned absolute against ångström data — there are no absolutes. Typed UFF rests and the global spring scale unify: they're both multipliers on the base bond length.

Key decisions: (1) normalization at engine init, one place, all engines adopt it; (2) persisted settings migrate from absolutes to multipliers (versioned localStorage schema); (3) scenario/test baselines re-anchored in normalized units (the YAML CaC beds make this mechanical). Trade-offs: engine change (the constraint says core pattern should avoid it — this IS the phase that justifies it, but it's the heavy option); every persisted setting and config preset needs migration; debugging gets harder (log lines in normalized units need base-scale context). **Probability 0.10. Complexity high.** Risks: migration bugs silently rescale existing users' layouts; normalized-unit debugging confusion; engine-internal rounding at extreme base scales (ångström × 1e4 vault spread).

## C5 — Eliminate the panel's settings role (layout is an attribute of the data source)

**Summary:** Layout configuration moves into the importer package/source declaration; the Layout panel shrinks to engine pick + play/pause — users never tune physics because sources ship their own regime.

The most radical reading of "packages, not crates": the molecular collapse defect existed because physics config lived far from the data it describes. Importer packages already declare schema and parsing; let them declare a layout regime too (`[layout] engine = "gpu-force", spring_len = 1.4, gravity = 0, seed = "authored"`). The SDF package ships its molecular regime; the vault source ships vault defaults; kubernetes ships its own. The panel shows what the source declared (provenance: "from sdf.toml"), offers engine override and play controls, and nothing else — adjustments, if any, are share-fragment/config-preset territory, not panel knobs.

Key decisions: (1) physics config lives with the data it configures — the coupling is the point; (2) panel minimalism as a feature (Operate mode: run/pause/engine, done); (3) escape hatch exists (?config= and share fragments) but is not in the panel. Trade-offs: interactive exploration ("what if more repulsion?") loses its home — a real regression for vault users who *do* tune; sources must author regimes (importer authors become layout designers); conflicts between source-declared and user-persisted settings need precedence rules. **Probability 0.05. Complexity low.** Risks: vault tuning workflow regresses badly (the main use case!); importer-package scope creep; users file "where did the sliders go" issues.

## C6 — Layout recipes in Monaco (GUI generated from a TOML recipe)

**Summary:** The panel's settings become a small TOML "layout recipe" edited in the Monaco surface the Importers panel already ships; GUI controls are generated from the recipe's declared parameters.

The app already has a Monaco-based TOML editing surface with sandboxed preview (Importers panel). C6 reuses it: a layout recipe declares parameters with bounds and defaults (`spread = { value = 1.0, min = 0.5, max = 2.0, intent = "Spread" }`), and the panel generates its controls from the recipe — the recipe is the form schema. Users edit either side (GUI writes recipe, recipe drives GUI). Regimes are recipe files; provenance is textual diff (`# from molecular-uff.toml`, `# your overrides`). Expert users get full expressiveness; casual users get generated GUI; one representation, two projections.

Key decisions: (1) reuse the Monaco/TOML infrastructure rather than invent a form system; (2) recipe = single source of truth, GUI is a projection; (3) recipe schema stays tiny (parameters + bounds + provenance comments) — not a programming language. Trade-offs: TOML editing in a GUI panel is expert-facing regardless of projections; generated-GUI schema work duplicates C2's manifest effort (converge them if both pursued); text-dirty/apply semantics in a live sim (when does the recipe re-apply?) need care. **Probability 0.06. Complexity medium-high.** Risks: two-projection sync bugs (GUI edit → recipe regen loses comments); Monaco bundle size for a settings panel; recipe-as-truth conflicts with localStorage persistence model.
