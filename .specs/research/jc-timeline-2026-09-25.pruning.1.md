## 1. Specification defect found while applying it — and the scale I used

`scoring.formula` reads `total = sum(weight_d * score_d) / 5, giving 1.0-5.0`. **Those two clauses cannot both be true.** The weights sum to exactly 1.000 and the scores range 1–5, so `sum(w*s)` *already* yields 1.0–5.0; dividing by 5 would yield 0.2–1.0. The `/5` is a typo, for three independent reasons:

1. The stated range `1.0-5.0` is only reachable without the division.
2. `essential_fail_cap: "…caps the total at 2.0"` is stated on the 1.0–5.0 scale; over a 0.2–1.0 scale a 2.0 cap could never bind, making the cap and the entire gating mechanism inert.
3. `rubric_dimensions[*].scale` is `"1-5"` per dimension, so a dimension-weighted sum on that scale lands in 1.0–5.0 by construction.

**Reading used throughout this report: `total = sum(weight_d × score_d)`, on the 1.0–5.0 scale, with no division.** This is recorded explicitly rather than silently resolved, because a colleague applying the `/5` literally would report totals 5× smaller than mine and the aggregate vote would be meaningless. Weights were verified to sum to exactly 1.000, so the un-normalized sum is already correctly scaled.

## 2. Method and interpretation rules applied (uniformly, before scoring)

These rules were fixed in advance and applied identically to all 18, so no proposal is advantaged by a lenient reading:

1. **Set-level constraint ≠ per-approach specification.** A statement in a set's "Constraints"/"Conventions" preamble (A:45, B:20, C:16/C:31) is *context*; it does not satisfy a checklist item that asks whether **the animated DAG view / the new panel** specifies something. A statement that describes *what the non-animated / non-store path actually does* does satisfy it, because the item asks for the behavior, not the requirement. This is why A1 ("swaps the pulse for a static highlight") and C (success criteria: "`prefers-reduced-motion` disables tweening") pass CK-004 while A2–A5 and B2–B6 do not.
2. **Explicit inheritance counts.** Where a proposal says a layer "is exactly A1's" (A6) or "identical to Approach 1" (B2, C2), that layer inherits A1/B1/C1's specification. Inheritance cannot supply a *new* specification the parent does not make (e.g. it cannot manufacture miss/overlap semantics).
3. **Unstated justification fails a gate.** CK-007 asks for reuse *or* a stated reason. Adding an endpoint while naming the existing surface elsewhere in the paragraph does not supply the reason. A3 ("Because `/progress` is per-source and already polled every ~250 ms by the app, 'live' comes free") and A2 ("…serves it through the same `/graph/*` buffers … so the canvas needs no new wire") are the models of a passing answer; A1/C1/C5/C6 add endpoints and never compare them to the existing route set.
4. **Acknowledging a landmine is not specifying its behavior.** CK-009 asks what the *user sees* on cap exceedance. "mitigate with the caps in `lib.rs`" states a mitigation for slowness, not an exceedance path. "wasm eval blocks the UI thread above the caps" states the failure the item forbids.
5. **Pitfall items are scored as defects** per `pitfall_handling`, capping the affected dimension at 2: CK-018/CK-020 → **D4**; CK-021/CK-022 → **D3**; CK-019 → **D5**.

## 3. Stage 2 — my reference result (written before scoring)

A correct proposal here must, before anything else: (a) add **one** field to `engine = "tvix"` on `format_version = 3` — a declared graph input — and let the existing typed `[[parser.variables]]` bind everything else at apply time, with the current graph arriving as *data* through the existing VFS so `render_expression` stays O(1) and `builtins.fromJSON` keeps laziness; (b) shape a `Transform` **trait** (not a concrete struct) in an existing crate or a single new wasm-clean crate, so the requester's topos can implement and consume it from outside — `apply(&VaultGraph, &RunCtx) -> Result<TransformOutput, TransformError>` with the output carrying both the graph *and* its `Vec<SearchDocument>` so transform output re-enters the discovery contract; (c) record a typed run — `(run_id, transform_id, bound variables, trigger, input_revision, output_revision, status, delta)` — in a **bounded ring in `AppState`** (never in `GraphSnapshot`), store a `RunDelta` of node-id lists, keyframe every K runs, and land each run's output as a **distinct addressable artifact** with the live graph published only on success; (d) make "upcoming" come from a **declared, serialisable plan** on the existing `WatchPlan` tick (`spawn_poll`) — a new `tokio` task, cron string, or cluster CronJob is the classic scope bomb — and state miss/overlap policy; (e) animate by **patching changed node/edge ranges into the existing GPU buffers** under the revision guard already in `graph_canvas::load`, carrying positions by **id** (not index), and give it a `prefers-reduced-motion` variant; (f) **restore the metadata being dropped** at `RawNode` and `convert_generated_graph` and put `facts` + `provenance` on the shared `NodeMeta` that `/node/*id` already serves, so every importer gains it; (g) run eval on the `spawn_blocking` path `POST /generate` already uses, under a `JC_MAX_*`/time budget, and **record a cap breach or timeout as a failed run with a visible reason**; (h) name concrete `file:line` seams, the `charts/jump-cannon/knowledge/` map update, and pair each of this repo's documented landmines (tvix 3-level closure bug, no fuel/step limit, `deepSeq` stalling the blocking thread, O(n²) `foldl'` attrset construction, non-atomic `/graph/*` fetches, the retired tvix-worker, the position-frame `FrameRing`) with a countermeasure that exists in the codebase; (i) demonstrate generality on a non-omp source; (j) slice into phases that each land on an existing seam and are usable the day they merge.

**No proposal in the field satisfies (g).** That is the single most important finding in this report.

## 7. Selection

### 7.1 Ranking as the spec's procedure produces it

Every total is 2.00, so the ranking *is* the tie-break: **D1, then D3, then D6.** B1 is first outright (D1 = 5, the only one). A1 and C1 then tie **exactly** on all three keys (D1 = 4, D3 = 4, D6 = 5), as do B2 and C2 below them (4, 3, 5).

### 7.2 Diversity requirement applied

The three top-of-ranking proposals — B1, A1, C1 — are three phrasings of one design. All three land phase 1 on the same seam: a transform package carrying a declared graph input, applied as a post-import stage in `crates/importer`, recorded in a run ledger inside graph-api, surfaced by a Runs panel, scheduled from the catalog on the existing poll tick. The spec's rule fires: *"If two selected proposals would land their first phase on the same seam, prefer the pair that differs in where the run state lives, and record the collision."*

- **B1 and A1 differ in where the run state lives** — B1 puts it in *"a `RunLedger` (ring in `AppState`, …)"* plus a JSONL file (b:69, b:139), a **durable** store; A1 puts it in a purely in-memory *"ring of N (default 256) alongside the last K (default 8) full snapshots"* (a:110), with *"No durability across restart (deliberate: bounded)"* (a:137) stated as a trade-off. B1 also introduces a new crate and a `Transform` **trait**; A1 deliberately introduces no crate — *"The Rust side is a `crates/importer` type, not a crate"* (a:102).
- **C1 collides with B1 on both** — C1's store is also *"a ring of the last N runs in `AppState`"* plus *"`appends one JSONL line to `<packages_dir>/runs.local.jsonl`"* (c:74), the same location and the same durability posture, and it lands on the same seam as an `Importer` decorator (`TransformedImporter<I: Importer>`, c:72).
- The next-ranked proposal that does **not** reintroduce the collision is **B2**, which puts run state in a third, genuinely different place — graph-vcs commits on a `MinigrafStore` (b:82) — with a higher raw total than C2 (3.566 vs 3.433) and the same tie-break key.

### 7.3 My ranked vote — top 3

**1. B1 — "Transform packages + run ledger in graph-api"** · final 2.00, raw 4.067 (highest raw after C1; first on D1 at 5)
*Two dimensions that carried it:* **D1 = 5** — the only proposal in the field whose run record and `Transform` trait both match the score_4 anchor, extended with `variables`/`status` and with `TransformOutput.documents` so a third party's output re-enters the discovery contract. **D4 = 5** — `render::apply_delta` + position carry-over keyed on id, the field's cleanest per-frame patch, with the wrong-reuse failure named.
*Weakest dimension:* **D3 = 2, capped by CK-022.** B1 stores the run record in a bounded `AppState` ring (good) but its timeline *"replays deltas from the ledger onto the current buffers"* (b:71) — a projection over the live graph, with no retained state and no publish guard, so a partial transform's effect on the served graph has no rollback. *What would raise it:* land each run's output as a distinct addressable artifact (a content-hashed snapshot or a `MinigrafStore` commit per run) and publish the live graph only on success — B2 already does this; the fix is to graft B2's store onto B1's crate and panel.
*First-phase kill criterion:* if `[parser] input = "graph"` cannot be added to `validate_config` without rejecting any existing `generate-*.toml`, or if injecting the current graph as a lazy VFS import costs more than ~O(n) at the 100k-node scale where `deepSeq` already stalls the blocking thread, kill the server-eval shape and fall back to B1's `graph-transform` crate as an `Importer` decorator with the ledger moved to C1's `AppState` + JSONL store.

**2. A1 — "Transform packages + run journal in graph-api"** · final 2.00, raw 3.967
*Two dimensions that carried it:* **D1 = 4** on a `data_loader::Transform` trait that a third party can implement without a new crate. **D6 = 5** — the anchor's shared-`NodeMeta` fields *plus* the root-cause fix (projecting the Nix `metadata` that `convert_generated_graph` discards today), which is what actually makes every node click informative.
*Weakest dimension:* **D7 = 3** — no phase structure; transform + journal + timeline + node content land as one bundle, and its most valuable slice (node content) is described only in the set-level footer rather than inside A1. *What would raise it:* restate A1 as P1 node-content-only (zero run dependency, answers the requester's node complaint for every source immediately), P2 manual one-shot transform + run record, then the timeline.
*First-phase kill criterion:* A1's `GET /runs` must first justify itself against `/progress?since=` — if a per-source bounded event window with `run_started`/`run_touched`/`run_finished` records serves the Runs panel as well as a bespoke endpoint (A3 says it will), **A1 collapses into A3** and A1 is a store, not a design.

**3. B2 — "Runs are graph-vcs commits; the History panel is the timeline"** · final 2.00, raw 3.566
*Selected over C1 by the diversity rule, not by score:* C1 ties A1 exactly on all three tie-break keys but collides with B1 on both the first-phase seam and the run-state location; B2 differs from both. On its own merits B2 is the field's best *durability* and *external-implementability* story (D1 = 4, D2 = 5, D6 = 5).
*Two dimensions that carried it:* **D2 = 5** and **D6 = 5** — identical package mechanism to B1 and a per-node `history` served as a store query, both inherited and both exact.
*Weakest dimension:* **D5 = 2, capped by CK-019** — `TransformSchedule` is a new scheduler duplicated across the session-manager world host and standalone graph-api, which B2's own risks concede (*"scheduler duplication between hosts"*). *What would raise it:* delete the second scheduler and drive the `TransformSchedule` from the existing `spawn_poll` tick that B1 already extends; then B2 = B1's contract + a durable store, and the two merge cleanly.
*First-phase kill criterion:* the standalone `graph-api --source=…` binary has no VCS store today; if embedding a per-source `MinigrafStore` makes *"every deployment grows a minigraf file"* (b:87) unacceptable for non-world users, the run history must fall back to B1's `AppState` ring + JSONL and B2 loses its reason to exist.

### 7.4 Displaced runner-up (recorded per the spec, not promoted)

**C1** ties A1 **exactly** on the complete tie-break key (D1 = 4, D3 = 4, D6 = 5) and has the **highest raw total in the field (4.100)**, yet is not in my top 3 solely because the diversity requirement forbids three phrasings of one design and C1 duplicates B1's first-phase seam *and* B1's run-state location. **If the orchestrator prefers the raw ranking to the diversity filter, the third slot is C1 and B2 is dropped** — C1 is the stronger proposal on the raw number and is tied on every key that the spec itself designates as the tie-break. C1's only scored defect is CK-007, the same unstated-endpoint-justification failure as A1.

### 7.5 Runner-up worth noting

**A3** (raw 3.633) scored D4 = 5 and is the cheapest genuinely-sliceable increment in the field, but it fails CK-004 (essential) and trips CK-022, and its run unit is a *rebuild* rather than a transformation applied to a graph revision (D1 = 3).
