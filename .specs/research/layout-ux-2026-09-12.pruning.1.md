Weights: PPH .25 / UCCG .20 / CFDD .15 / OML .15 / RMR .13 / KM .12. Essential gate: any of CK-001/002/003 = NO → cap 2.00, label ≤ hold. Pitfalls CK-010/011/012 YES → −0.25 each, floor 1.0. Tie-breaks: (1) PPH, (2) UCCG, (3) fewer YES pitfalls.

## TOP-3 VOTE (ranked)

1. **C2 — Engine capability declarations** (3.85) — The only proposal whose mechanism makes the lying knob *unrepresentable for every engine*, local or remote: applicability truth moves into per-engine manifests (served with `/compute/engines` for remotes, serde-generatable for locals), so `spring_len` at 25/25 UFF-typed bonds and the backend selector at 24 nodes are never constructed. It is the score_4 anchor of Use-Case Coverage almost verbatim ("remote engines contribute their own settings through the same capability pass"), has the most honest risk section (manifest/Rust drift + serde-generation mitigation, schema creep, degraded-but-honest fallback for non-adopting remotes), and costs no engine change. Its weaknesses are real but bounded: local manifests are new compiled per-engine content (CK-005 NO) and it shows control *absence* rather than per-parameter provenance text (CK-006 NO) — both are exactly what the full-development phase should fix, ideally by merging C1's regime capsules into the manifest renderer.
2. **B1 — Intent sliders as dimensionless multipliers** (3.62) — The strongest *interaction* model: Spread/Stiffness/Settle multiply whatever base resolved (UFF data, `for_n_nodes`, boot preset), so the vault-unit/ångström collision is unrepresentable rather than relabeled ("it cannot collide with data the way absolute constants do"). It is the only high-probability proposal that explicitly claims all six use cases *and* designs for the hard one ("remote engines with non-force settings schemas need per-engine intent mappings or the sliders gray out" — a named graceful degradation). Write-through into the existing `GpuForceOptions` means no engine change. It loses to C2 on provenance: nothing shows the user *that* the base is data-owned (CK-006 NO), and multiplier persistence across regime switches is an admitted open design question (CK-009 NO).
3. **C3 — Per-graph-class forms** (3.38 after −0.25 CK-010 penalty) — The only proposal that explicitly and honestly covers all six cases end-to-end: Vault form (today's sliders, honest there), Molecular form (UFF summary, geometry scale, keep-authored-3D; no cooling/halt/backend), Remote form (settings JSON rendered generically), Static form (solve + quality preset). Shared slider-row/provenance-chip components keep it one meta-pattern, but it *is* the bespoke-per-class pitfall CK-010 names (hence the penalty, and KM 2), and its answer to a seventh graph class is "write a new form" — the weakest generality story of the three. It earns rank 3 because its coverage is explicit and verified against the brief rather than asserted.

First alternates (hold): **C1 — Regime-as-data registry** (3.80 pre-gate, capped 2.00 — silent on remote/static) and **A2 — Engine/Regime/Intent three-band** (3.42 pre-gate, capped 2.00). If either select proposal falters in development, C1 is the strongest merge candidate: its regime-registry capsules supply exactly the per-parameter provenance display and preset quarantine that C2 lacks.

## GATE ANALYSIS (CK-001, the decisive item)

CK-001 YES requires the proposal text to explicitly address all six use cases, including the two the rationale flags as commonly dropped (remote engines, static solvers). Only three proposals clear it:

- **B1 YES**: "few intents, each with a real, testable effect across all six use cases" + explicit remote handling ("per-engine intent mappings or the sliders gray out").
- **C2 YES**: "Every engine ships a capability manifest" (static solvers are engines; their manifest simply declares one-shot controls) + remote manifests "served alongside `/compute/engines`" + fallback form for non-adopters.
- **C3 YES**: four named forms include "Remote form: the engine's own settings JSON rendered generically" and "Static form: solve button + quality preset only"; generated/untyped graphs fold into the Vault form via the same class-detection predicates.

Everything else is NO on textual silence (A1–A5, B2–B6, C1, C4–C6) or explicit self-exclusion: A6 admits "remote engines' settings have no selection analog at all"; B5 scopes itself to "live sims"; C4 claims "all engines adopt it", which is contradicted for third-party remote engines (a universal claim with a visible false instance excludes YES). C1's registry could express remote/static regimes but its text limits option typing to "the same serde coverage the options structs have" — local structs only.
